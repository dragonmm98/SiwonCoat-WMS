Overview & context

Read this first. It frames everything else — what you're building, the boundary of the MVP, the stack, and the non-negotiable rules that keep inventory trustworthy.

What Jably WMS is

Jably WMS is a warehouse management system that runs the full inventory lifecycle for a fulfillment center: setting up the physical warehouse, registering products, receiving supplier deliveries, storing stock, and picking, packing, and shipping customer orders. It is built as a modular monolith — one deployable NestJS backend with clear internal module boundaries — plus one Next.js progressive web app that serves both the desktop operations console and the touch-friendly scanner screens. There is no separate mobile app; the same web codebase adapts to warehouse scanner hardware.

The guiding principle is inventory correctness. Physical stock is money, and two workers must never be able to sell or move the same unit twice. Every design choice below exists to protect that.

Core conventions & invariants

UUID keysEvery operational row uses a UUID primary key.
Decimal quantitiesStock quantities are Decimal(18,3) — never floating point.
Optimistic versionConcurrency-sensitive rows carry version; updates guard on it and increment it.
Append-only ledgerEvery stock change writes an InventoryTransaction in the same DB transaction as the balance mutation.
availableQtyAlways derived as onHandQty − reservedQty; never stored or edited directly.
IdempotencyScanner mutations carry a key; replays return the original result instead of doubling up.
Transactional outboxEvents for jobs/sockets/projections are written in the same transaction, not fired directly.
No hard deletesAll FKs are onDelete: Restrict; state changes via named commands, never destructive deletes.
Named commandsState transitions happen through explicit commands (approve, allocate, pick…), not generic CRUD updates.

Glossary

SKU
Stock-keeping unit — one distinct product.
Lot
A batch of a SKU, often with a shared expiry date.
Location / bin
A scannable physical spot inside a zone.
On-hand
Physical quantity present at a balance.
Reserved
On-hand quantity promised to orders.
Putaway
Moving received stock from receiving into storage.
Allocation
Reserving specific stock to fulfill an order.
FIFO
First-in-first-out: consume oldest stock first.
FEFO
First-expired-first-out: earliest expiry first.
Pick
Collecting reserved items for an order.
Wave
A batch of orders released to pick together (later phase).
Ledger
The immutable history of every stock movement.

The critical path — how a scanned stock change becomes durable, explainable state:

Operator scans in the PWA; the request carries an idempotencyKey.
Next.js forwards it same-origin via /wms-data to the API.
A controller routes it; the ValidationPipe rejects any unknown or malformed field.
The service opens a single prisma.$transaction.
It updates the balance only if version is unchanged (optimistic lock) — else a conflict is returned.
In the same transaction it appends an immutable InventoryTransaction ledger row.
Still same transaction: an AuditLog row and an OutboxEvent are written, then it commits atomically.
The response returns the updated resource and its new version; retries with the same key are safe.

Invariant: stock never changes without a ledger row in the same transaction. Redis, queues, and sockets are never the source of truth.
