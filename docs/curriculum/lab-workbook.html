05

The inventory kernel & the ledger

Goal: understand the transactional adjustment, then write a move command that keeps the ledger consistent.

Crux · Buildfull day
This is the heart of the whole system. Read docs/adr/0002-inventory-invariants.md before touching code.
Read first

Study apps/api/src/inventory/inventory.service.ts → createAdjustment. It shows the whole pattern in one method:

inventory.service.ts · createAdjustment (the pattern)
await this.prisma.$transaction(async (tx) => {
  // 1. optimistic lock: only update if version is unchanged
  const updated = await tx.inventoryBalance.updateMany({
    where: { id: current.id, version: current.version },
    data: { onHandQty: resultingOnHand, version: { increment: 1 } },
  });
  if (updated.count !== 1) throw new ConflictException("Inventory changed…");

  // 2. append an immutable ledger row IN THE SAME TRANSACTION
  await tx.inventoryTransaction.create({ data: { type: "ADJUSTMENT", … } });

  // 3. audit + 4. outbox event, also same transaction
  await tx.auditLog.create({ … });
  await tx.outboxEvent.create({ … });
});
Observe
run an adjustment, then read the ledger
# grab the seeded balance id:
BAL=$(curl -s localhost:4000/api/v1/inventory-balances | jq -r '.[0].id')
curl -s -X POST localhost:4000/api/v1/inventory-adjustments \
  -H 'content-type: application/json' \
  -d "{\"balanceId\":\"$BAL\",\"direction\":\"INCREASE\",\"quantity\":10,
       \"reason\":\"Cycle count\",\"notes\":\"\",\"idempotencyKey\":\"$(uuidgen)\"}" | jq
# the response includes the updated balance AND its recent transactions
Build
  1. Add a POST /inventory-moves endpoint + service method createMove that moves quantity from one location's balance to another.
  2. In one $transaction: decrement the source balance (optimistic lock), upsert the destination balance, and write one MOVE ledger row with fromLocationId and toLocationId. Reject if the source lacks available stock.
Checkpoints
  • After an adjustment the balance version increments by 1 and a matching ledger row exists.
  • Your move is atomic: total on-hand across both locations is unchanged, and one MOVE transaction records it.
  • A move larger than available stock is rejected — nothing is written.

06

Concurrency & idempotency

Goal: prove with tests that inventory can't go negative under a race, and that scanner retries are safe.

Crux · Buildfull day
Concepts
  1. Optimistic concurrency — the where: { version } guard from Day 5. If updated.count !== 1, someone else won the race → conflict.
  2. Idempotency — every scanner mutation carries an idempotencyKey. A unique constraint on the ledger makes a replayed key fail with P2002, which the service maps to a safe conflict.
Build the tests

Create apps/api/src/inventory/inventory.concurrency.spec.ts against a real test database.

inventory.concurrency.spec.ts (skeleton)
it("cannot over-decrement under concurrency", async () => {
  // seed a balance with onHand=10, reserved=0
  const results = await Promise.allSettled([
    service.createAdjustment({ balanceId, direction:"DECREASE", quantity:8, … }),
    service.createAdjustment({ balanceId, direction:"DECREASE", quantity:8, … }),
  ]);
  const ok = results.filter(r => r.status === "fulfilled");
  expect(ok).toHaveLength(1);          // exactly one wins
  // on-hand never goes below reserved / below zero
});

it("replaying an idempotencyKey is rejected, not double-applied", async () => {
  const key = randomUUID();
  await service.createAdjustment({ …, idempotencyKey: key });
  await expect(service.createAdjustment({ …, idempotencyKey: key }))
    .rejects.toThrow(ConflictException);
});
run
pnpm --filter @wms/api test
Checkpoints
  • The concurrency test shows exactly one of two racing decrements succeeds.
  • On-hand never drops below reserved in any run.
  • Replaying the same idempotencyKey is rejected and does not apply twice.
StretchExplain to a peer why Redis or a WebSocket event must never be the system of record for stock.

Build receiving → the ledger

Goal: a PO can be received into a staging location, posting real stock and a ledger row.

InboundBuildfull day
The repo already creates purchase orders (apps/api/src/inbound/inbound.service.ts) but does not yet post receipts. That's today's build — apply the Day-5 transaction pattern to inbound.
Read first
  1. PO state machine: DRAFT → OPEN → PARTIALLY_RECEIVED → RECEIVED → CLOSED.
  2. Re-read createAdjustment — your receipt-posting will use the same $transaction + ledger + upsert shape.
Build
  1. Create a PO through the console (or API) with one line for SKU DEMO-001.
  2. Add POST /purchase-orders/:id/receipts with a service method postReceipt. For each received line, in one $transaction: upsert an InventoryBalance at the RECEIVING location, insert an InventoryTransaction of type RECEIPT, and advance the PO status to PARTIALLY_RECEIVED or RECEIVED based on received vs expected.
  3. Capture a discrepancy path: if received < expected, keep the PO at PARTIALLY_RECEIVED.
Checkpoints
  • Receiving a full PO moves it to RECEIVED and creates stock at the receiving location.
  • Every received unit is explained by a RECEIPT ledger row — no stock appears without one.
  • A partial receipt leaves the PO at PARTIALLY_RECEIVED.
StretchGenerate a simple putaway step: a second command that moves the received stock from RCV-01 to a STORAGE location (reuse your Day-5 move).

08

Build FIFO/FEFO allocation

Goal: allocating a sales order reserves real stock — and two orders can't over-reserve it.

OutboundBuildfull day
The repo creates sales orders (apps/api/src/outbound/outbound.service.ts) but allocation isn't implemented. Build it today.
Read first
  1. Order flow: DRAFT → READY_TO_ALLOCATE → ALLOCATED → PICKING → PICKED → PACKED → SHIPPED.
  2. Availability rule: available = onHandQty − reservedQty. Allocation increases reservedQty; it never touches on-hand.
Build
  1. Add POST /sales-orders/:id/allocate → allocate(orderId).
  2. For each order line, select candidate balances with available > 0, ordered FIFO (oldest first) — or FEFO (earliest expiresAt first) when the SKU is expiryTracked. Iterate deterministically to reduce deadlocks.
  3. Reserve against each balance with the optimistic-lock guard (where: { version }, increment reservedQty and version), write a RESERVE ledger row, and set the order to ALLOCATED. If demand can't be fully met, reject the whole allocation.
Checkpoints
  • Allocating raises reservedQty and drops available by the ordered amount.
  • An expiry-tracked SKU allocates the earliest-expiring lot first (FEFO).
  • Two orders competing for the last units → only one succeeds; the other is cleanly rejected.
StretchAdd a release command that reverses a reservation (decrement reserved + RELEASE ledger row) for cancelled orders.
